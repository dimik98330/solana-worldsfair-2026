## Шесть направлений

### 1. Выплаты долей маленькой команде через свой checkout

**Гипотеза пользователя:** 2–3 разработчика/художника уже принимают криптоплатежи за общий цифровой результат и хотят видеть, что один заказ оплачен сразу всем. **Почему Solana:** прямое публично проверяемое распределение onchain-актива без посредника, временно удерживающего всю сумму. Обычная база сохранит расчёт долей, но не выполнит такой расчёт средствами на Solana.

**Минимум:** одна транзакция, несколько стандартных переводов тестового SOL либо одного обычного тестового SPL mint, короткий order reference при необходимости (T1–T3). Собственная программа не нужна для разовой выплаты по явно показанным адресам. Нужна дополнительная логика/готовый контракт, если обещаем неизменяемое соглашение, onchain order uniqueness, будущие начисления, возвраты или блокировку изменения долей.

**Подписант/доверие:** покупатель подписывает всю транзакцию; средства уходят прямо участникам, оператор не хранит их. Покупатель доверяет отображению адресов/сумм; участники доверяют источнику заказа и согласованию долей. Повтор новой транзакции с тем же order ID сам по себе блокчейном не запрещён. Повторное нажатие/неясное подтверждение нельзя лечить слепым повторным платежом.

**Демо после разрешения разработки:** тестовая покупка, одна подпись, три изменившихся баланса и одна transaction signature; отмена подписи не создаёт выплату. Зависимости — RPC, кошелёк, test SOL; fiat rails и игровые платформы не нужны. **Вывод о двух днях:** наиболее реалистично при жёстком сужении. **Причина отказаться:** целевым командам нужны именно деньги из Steam/Roblox/банка или юридически гарантированные роялти — этот checkout их не решает. **Fallback:** ограничить демо SOL и тремя заранее проверенными адресами, не выдавать последовательные выплаты за атомарные.

### 2. Проверяемая история ремонта/гарантии и отзыв записи

**Гипотеза:** маленькая мастерская выдаёт проверяемую запись, покупатель подержанного устройства проверяет её вне сайта мастерской. **Почему Solana условно:** общий реестр issuer/status имеет смысл при нескольких независимых выдавателях/проверяющих. Для одной мастерской обычный подписанный документ и её база могут быть достаточны. Хеш документа не доказывает ремонт, качество, право на гарантию или соответствие QR конкретному физическому предмету.

**Минимум-кандидат:** готовый SAS — issuer credential, одна schema, одна attestation; отзыв через close (T5–T7). Собственная программа не нужна, если его модель удовлетворяет узкому сценарию. Документы и личные данные не выкладывать в публичную цепочку; использовать синтетический device ID/контент для демо. Нельзя обещать долговечную историю лишь наличием текущего account: нужны сохранённые ссылки/доказательства выпуска и интерпретация закрытия.

**Подписант/доверие:** мастерская подписывает выпуск/отзыв; клиент проверяет заранее известный issuer, не просто любое имя. Реальное подтверждение мастерской и связь устройства с ID остаются offchain-задачами. Ошибка RPC/отсутствие account на неверной сети — не доказательство отзыва.

**Демо-кандидат:** issuer выпускает запись; verifier видит её; issuer закрывает; повторная проверка с доказанным исходным выпуском больше не считает запись действительной. **Два дня:** условно возможно только если первая проверка выбранного SAS SDK проходит быстро. **Отказ:** не удалось воспроизвести issue→verify→close либо нет убедимого независимого verifier. **Fallback:** подписанный документ + явная локальная демонстрация статусов, помеченная как offchain-прототип; она не доказывает работающую Solana-интеграцию и не заменяет обязательную devnet-транзакцию.

### 3. Escrow одного этапа работы

**Гипотеза:** заказчик резервирует сумму и выпускает её исполнителю после подтверждения. **Почему Solana:** проверяемое удержание цифровых средств по программным правилам (T4). **Минимум:** PDA/хранилище, депозит, разрешённый release/refund и доказуемые правила переходов. Стандартного обычного перевода с memo для escrow недостаточно.

**Подписант/доверие:** заказчик финансирует и подтверждает release; программа контролирует хранилище. Арбитр, таймауты, upgrade authority и доступ к возврату — отдельные доверительные предположения. Нельзя назвать систему бездоверительной при операторском ключе, способном забрать деньги. Качество работы onchain не определяется автоматически.

**Демо-кандидат:** deposit→попытка release чужим ключом отклонена→release надлежащим подписантом. **Два дня:** не рекомендовано новичку при отсутствующем toolchain и непроверенном готовом escrow. Нужны отрицательные тесты и разрешение неоднозначного refund. **Fallback:** обычная выплата после подтверждения уже не escrow; следует отказаться от escrow-позиционирования, а не переименовать перевод. Стоимость стороннего протокола/его devnet-доступ не установлены.

### 4. Квитанции и сверка покупок API для AI-агента

**Гипотеза:** разработчик хочет связать оплаченный запрос с конкретным ответом и исключить повторную оплату при retry. **Почему Solana:** независимо проверяемое урегулирование onchain-платежа. Для API с обычным централизованным биллингом отдельная Solana-запись может быть декоративной; подпись оплаты не доказывает качество/доставку ответа.

**Минимум-кандидат:** один собственный детерминированный API-ресурс, один клиент и один test mint; стандартный перевод и проверяемая запись покупки либо корректный x402 V2 flow (T8–T9). Собственная onchain-программа для обычного платежа не нужна. Memo/tx signature не обеспечивают сами application-level idempotency. x402 уже имеет платёжный response; новое отличие должно касаться конкретной сверки/повторной обработки, а не существования квитанции.

**Подписант/доверие:** покупатель подписывает явно разрешённый платёж; автономное хранение сервером ключа пользователя и неограниченный spending не входят в простой MVP. Доверие продавцу за содержимое ответа остаётся; facilitator не удостоверяет качество AI. **Демо:** тестовая покупка возвращает ресурс, запись связывает request ID с подтверждённой транзакцией; повтор запроса возвращает тот же результат без новой оплаты. **Два дня:** условно, если конкретный SDK/protocol тест проходит в первый рабочий блок. **Fallback:** собственный локальный API без платной AI-модели; не обещать интеграцию с OpenAI или сторонними платными API. Self-facilitation возможна по документации; цена/бесплатный доступ managed facilitator неизвестны.

### 5. Купоны и погашение токенизированных облигаций

**Гипотеза:** issuer/operator выполняет выплаты держателям на record date и погашение. **Почему Solana:** когда сами облигации и расчётный актив onchain, события можно сверять с учётом держателей. Если реестр/деньги фактически offchain, источник истины и исполнитель всё равно внешние.

**Минимум честного демо:** синтетический выпуск, заранее фиксированная модель держателей, тестовый расчётный token и реальная выплата. Но snapshot прав, переносы, округление, double claim, insufficient funds, redemption/burn, кто инициирует событие и допускает держателей — существенные части поведения. T10 опровергает shortcut «включим interest-bearing и купоны готовые».

**Подписант/доверие:** issuer финансирует и утверждает событие; держатели подписывают claim/redeem, если выбран такой процесс. Onchain не подтверждает платёжеспособность issuer или законность выпуска. **Два дня:** полноценное соответствие KASE не оценено — полное задание, данные, API/sandbox и критерии неизвестны этой роли. **Отказ сейчас:** слишком много непроверенных требований и финансовой логики для обещания завершённости. **Fallback:** явно синтетическая учебная симуляция с одним событием; это не доказательство KASE-интеграции. Реальные бумаги/деньги не разрешены.

### 6. Узкий помощник отзыва обычных token delegates

**Гипотеза:** владелец devnet-кошелька хочет увидеть, кому делегирован расход определённого SPL-токена, и отозвать это разрешение. **Почему Solana:** источник полномочий — token account в сети; база приложения не может его отменить.

**Минимум:** read token accounts, показать delegate/лимит и выполнить штатный Revoke (T11). Только классический SPL Token, явный список поддерживаемого; Token-2022 permanent delegate не отзывается владельцем и исключается (T12). Своя программа, индексатор, база мошенников и подписка на security API не нужны для такого объёма.

**Подписант/доверие:** владелец подписывает точечный revoke; оператор не получает токены и не хранит ключ. Адрес без известного имени показывается как неизвестный, а не как мошенник. **Демо:** на синтетическом token account заранее создан delegate; после revoke account показывает отсутствие delegate, повторная тестовая transfer-by-former-delegate отклоняется. Последняя проверка требует отдельного безопасного тестового контекста, не чужих ключей.

**Два дня:** технически наиболее коротко наравне с прямой выплатой; продуктовая дифференциация слабее, конкуренты ещё не изучены этой ролью. **Отказ:** пользователи уже удобно решают задачу текущим кошельком/инструментом или ожидают защиту всей истории/всех программ. **Fallback:** read-only explanation для unsupported account; не выдавать отсутствие обычного delegate за общую безопасность кошелька.

## Стоимость, доступ и ёмкость

**Допущение для сравнения:** два дня по 8 сосредоточенных часов = 16 часов человека с помощником. Это не подтверждённая доступность пользователя.
