## Опровергающие вопросы и сравнение пяти направлений

| Направление | Что может уничтожить ценность | UX/демо-вывод, пока предварительный |
|---|---|---|
| Доли небольшой indie-команды, только собственная страница оплаты | Команда получает почти всё через платформы, которые этот flow не контролирует; участники не хотят кошельки; ручной перевод и таблица уже достаточны | **Первый UX-кандидат:** один плательщик, одна подпись, три наблюдаемых поступления. Сначала проверять доступ к командам и их реальный канал денег |
| Проверяемая история ремонта с передачей записи | Покупатель не знает issuer; неверные сведения остаются неверными после подписи; мастерская не станет менять процесс | **Второй UX-кандидат:** чтение без кошелька, наглядный issuer и статус отзыва. Передача записи не означает переход права собственности или гарантии |
| Квитанции одной покупки API | Владелец уже видит платежи и логи; запись не доказывает правильный ответ; все новые SDK скрывают боль; никто не готов менять интеграцию | **Третий UX-кандидат:** одна покупка и связанная квитанция. Доказательство оплаты и получение ответа показывать раздельно |
| Escrow одного этапа | После разногласия нет приемлемого способа разблокировать средства; заказчик может не принимать результат; исполнитель может ничего не передать | Отложить для первого проекта: понятный happy path скрывает самый важный UX — спор, возврат и ожидание. Таймер сам по себе спор не решает |
| Купоны/погашение облигации | Неизвестны полномочия, источник держателей, record date, правила и полное задание KASE | Не финалист по текущему evidence: таблица выплат даёт красивое демо, но не подтверждает полезный корпоративный процесс |

Это порядок по простоте объяснения и полноте короткого сценария, не рейтинг спроса. Конкурентный анализ и техническая оценка ведущего агента могут изменить порядок.

## Общие принципы будущих сценариев

Первое чтение результата — без подключения кошелька. Перед подписью пользователь видит действие, сеть **Solana Devnet**, адреса, сумму, получателей и отдельно оценку комиссии. Фикстуры называются «Демонстрационные данные»; devnet-суммы — «тестовый SOL, без денежной стоимости». Нельзя показывать значок подтверждения только потому, что кошелёк закрылся.

Официальная документация подтверждает: транзакция может включать несколько инструкций; при ошибке одной изменения всей транзакции откатываются, но комиссия может списаться [S1]. Комиссии оплачиваются в SOL [S2]. Это даёт основу для сценария, но не доказывает, что наше приложение его реализует.

| Состояние | Предлагаемый текст и поведение |
|---|---|
| Нет кошелька | «Для просмотра кошелёк не нужен. Для отправки нужен отдельный тестовый кошелёк». Инструкция только по официальной ссылке; никакого ввода секретов в приложении |
| Неверная сеть / недостаточно средств | «Нужен Devnet» / «Не хватает тестового SOL на сумму и комиссию». Не предлагать покупку реальных средств |
| Ожидаем подпись | «Проверьте получателей и сумму в кошельке». Отдельная отмена до отправки |
| Подпись отклонена | «Вы отменили подпись. Эта операция не отправлена». Значения формы сохранены |
| Отправлено, результата ещё нет | «Транзакция отправлена. Проверяем результат». Ссылка на её реальную signature; без кнопки, создающей новый платёж |
| RPC недоступен / статус неизвестен | «Пока не удалось проверить результат. Не отправляйте повторно». Повторная проверка существующей signature, а не повторная покупка |
| Ошибка выполнения | Причина человеческим языком; «Перевод не выполнен; комиссия сети могла списаться». Исправление и новая попытка только после установленного исхода предыдущей |
| Подтверждено | Обновлённое состояние из сети + signature + Explorer с `cluster=devnet`. Если достигнуто `confirmed`, не называть это `finalized` [S5] |
| Отмена после отправки | Закрыть экран можно, гарантированную отмену транзакции обещать нельзя. Сохранять возможность вернуться к статусу; возврат — отдельное действие по правилам продукта |

Публичный devnet RPC ограничивает запросы; devnet допускает сбросы, тестовые токены не являются настоящими [S3]. Предлагаемая демонстрационная подготовка после будущего разрешения на разработку: заранее пополненные отдельные test wallets, проверенный RPC, реальные signature из репетиции, экран восстановления. Записанный проход маркируется как запись с датой; он не выдаётся за текущий live success. Mock/offline-режим явно маркируется и не заменяет blockchain-функцию.

## Кандидат 1: один платёж распределяется между участниками

**Гипотеза пользователя:** маленькая indie-команда уже принимает оплаты/поддержку через собственную ссылку и сверяет доли вручную. Базовая альтернатива для эксперимента — таблица долей и три последовательных перевода. Спрос не подтверждён.

**Законченный узкий сценарий:** плательщик открывает страницу команды → проверяет три адреса и неизменяемую для этой операции схему 50/30/20 → подключает тестовый кошелёк → подписывает один перевод → участники открывают общую квитанцию и видят поступления. Получателям не нужна подпись для получения; им нужны заранее согласованные адреса. Плательщик подписывает и платит комиссию. Политика изменения долей должна быть видимой; совместное управление долями в этот узкий flow не входит.

**Предложенные 3 экрана:** страница команды и долей; проверка платежа; итоговая квитанция. Демонстрационный пример: 0,1 devnet SOL распределяется как 0,05 + 0,03 + 0,02, комиссия отдельно. Это синтетический пример, не выручка.

**Devnet-момент:** одна подтверждённая транзакция с ожидаемыми переводами на три адреса; все три результата открываются по той же signature. В одном экране видно, кому и сколько ушло. Подлинность суммы подтверждается чтением транзакции, не только изменением счётчиков UI. Согласованные доли и их соблюдение — отдельное требование будущей технической проверки; набор переводов сам по себе не доказывает неизменяемость схемы.

**Предложенный хронометраж:** 0:00–0:20 проблема и предел собственного канала; 0:20–0:45 доли и сумма; 0:45–1:20 подпись/ожидание; 1:20–2:05 поступления и Explorer; 2:05–2:35 восстановление статуса и ограничения; 2:35–3:00 запас. Время не измерялось.

**Границы честности:** не «автоматически делим доход Steam/Roblox», не «гарантированная прибыль», не «юридическая доля», не «поступления невозможно скрыть вообще». После успешно отправленного платежа нет универсального Undo: ошибочный адрес требует отдельного возврата получателем, если он согласится. Если ценность оказывается только в удобной форме трёх переводов, отличимость продукта остаётся слабой.

## Кандидат 2: покупатель проверяет происхождение записи ремонта

**Гипотеза пользователя:** покупатель конкретного подержанного устройства хочет проверить запись известной ему мастерской при перепродаже. Альтернатива — бумажный чек/фото и звонок в мастерскую. Наличие доступа к мастерской неизвестно.

**Законченный узкий сценарий:** мастерская публикует запись о конкретном демонстрационном устройстве → текущий держатель открывает её → при передаче устройства переводит держание записи на согласованный адрес покупателя → покупатель открывает ссылку и проверяет issuer, содержание, нового держателя и актуальный статус отзыва. Публикацию подписывает issuer и платит её комиссию; передачу — текущий держатель с отдельной комиссией. Покупатель читает без подписи; получение записи не доказывает его согласие с условиями. Отзыв подписывает issuer, не продавец.

**Предложенные 4 экрана:** подготовка записи мастерской; публичная проверка; проверка передачи; результат передачи. Должны быть отдельные надписи «Подпись issuer проверена», «Issuer добавлен вручную для демо», «Запись действующая/отозвана». Подтверждённый адрес не равен проверенной коммерческой репутации. Только синтетический идентификатор устройства; ФИО и полный серийный номер не публикуются.

**Devnet-момент:** на уже выпущенной и обозначенной как подготовленная записи выполнить настоящую передачу; после перезагрузки публичной страницы видно нового держателя, а исходный issuer и история сохранены. Отдельная подготовленная отозванная запись показывает отрицательную проверку. Это одна live-подпись в демо; выпуск и отзыв — реальные предварительно выполненные операции, если будущая реализация это действительно подтвердит. Отзыв должен проверяться при каждом актуальном чтении; старый screenshot не считается доказательством действительности.

**Предложенный хронометраж:** 0:00–0:25 ситуация перепродажи; 0:25–0:55 issuer и содержание; 0:55–1:40 передача; 1:40–2:15 проверка новым держателем; 2:15–2:40 отрицательная проверка отозванной записи; 2:40–3:00 запас. Не замерено.

**Границы честности:** подпись доказывает, кто сделал заявление, а не факт качественного ремонта. Передача записи не подтверждает доставку вещи, право собственности или переход гарантии. Гарантийные условия не трактовать юридически. Простая ссылка на PDF без проверки подписи/отзыва не выполняет обещание. Ошибочная передача — не кнопка отмены; нужен отдельный обратный перевод текущего держателя. Если без доверенного issuer ценность пропадает, остановить массовый потребительский вариант и сначала проверить доступ к одному issuer.

## Кандидат 3: одна API-покупка и проверяемая квитанция

**Гипотеза пользователя:** разработчик, оплачивающий API-запросы, не может быстро сопоставить конкретное списание и запрос. Альтернатива — счёт провайдера + request ID в логах. Наличие такой боли неизвестно.

**Законченный узкий сценарий:** человек выбирает одну фиксированную операцию собственного демонстрационного API → видит цену и предмет → подписывает devnet-оплату → получает ответ → открывает квитанцию, связывающую request ID, продавца, сумму, signature и хеш ответа. Владелец кошелька подписывает конкретную оплату и платит комиссию. Продавец не получает право скрытно расходовать кошелёк. Просмотр квитанции не требует подключения.

**Предложенные 3 экрана:** заказ и цена; получение ответа; квитанция/сверка. Разделить «Оплата подтверждена» и «Ответ получен»: при оплате без ответа показать уже оплаченную операцию и восстановление выдачи того же заказа. Нельзя предлагать повторную оплату как средство исправить сетевой таймаут. Правило возврата должно быть отдельным явным условием; в узком демо автоматический возврат не обещается.

**Devnet-момент:** действительный платёж собственного test API и сопоставление подтверждённой суммы с одной квитанцией. Изменение демонстрационного ответа после оплаты приводит к несовпадению хеша, видимому пользователю. Это полезно только если квитанция действительно привязана к оплате и данным проверяемым способом; текстовая карточка в БД такой гарантии не даёт. API может быть локальным, детерминированным и бесплатным для автора; это честно объявленный demo merchant, а не платная интеграция с чужим провайдером. Не требуется вызывать оплачиваемую AI-модель.

**Предложенный хронометраж:** 0:00–0:25 проблема сверки; 0:25–0:55 операция и цена; 0:55–1:35 подпись/ответ; 1:35–2:05 связанная квитанция; 2:05–2:35 обнаружение изменения ответа; 2:35–3:00 запас. Не замерено.

**Границы честности:** квитанция не доказывает полезность/истинность ответа, получение его человеком или поддержку произвольного API. Это один ручной запрос; название «автономный AI-агент» было бы преждевременным. Если требуется новая сложная схема делегирования оплаты или custom settlement ради демонстрации, направление теряет преимущество простоты.

## Мобильная пригодность

Предлагается адаптивный web, без обязательного нативного приложения. Квитанции, доли и история должны читаться на телефоне без кошелька; длинные адреса сокращаются визуально, но доступны целиком перед подписью. На маленьком экране сначала сумма/сеть/получатель, затем вторичная информация. QR дополняет ссылку, не заменяет её на одном устройстве.

MWA официально соединяет dApp и мобильный кошелёк для подписей [S4]. Это не доказательство одинаковой поддержки всех телефонов: в разделе Local URI спецификации поддержка iOS ещё обозначена как будущая; речь именно об этом механизме, а не о всех способах подключения кошельков на iOS [S6]. Не обещать «работает везде». После выбора идеи понадобится проверка конкретных wallet/browser/OS; desktop-demo с проверенным кошельком остаётся меньшим объёмом работ. Потеря фокуса после перехода в кошелёк не должна стирать заказ или запускать повторную оплату.

## Дешёвый тест, который может опровергнуть выбор

**Рекомендация сейчас:** `target: test`, условно начать с направления долей после выбора пользователем. Доверие низкое по спросу; выше по ясности предлагаемого сценария. Не начинать код только ради получения «положительной» оценки. Доступ к участникам пока гипотеза; сообщений людям этот агент не отправлял.

**Рекрутинг отдельным сигналом:** владелец по собственному решению приглашает максимум 10 людей из доступных ему indie/game-dev контактов, которые реально участвовали в небольшой команде и согласовывали распределение дохода за последние 6 месяцев. Канал пока не подтверждён. Зафиксировать `получено согласий / приглашено подходящих людей`; не считать отсутствие ответа отсутствием проблемы. Цель — 5 подходящих сессий. Если контактов нет или сессий меньше 5, результат пользовательского теста — `inconclusive`, а отсутствие доступа становится отдельным ограничением пути к первым пользователям.

**Протокол до разработки:** по 15 минут на человека, максимум 5 сессий и до 30 минут сводки: 75 + 30 = 105 минут работы ведущего, без времени рекрутинга. Сначала попросить описать последний реальный расчёт и показать обезличенный пример; затем сравнить их текущий способ с текстовым сценарием выше. Порядок показа альтернатив чередовать, не обещая статистический A/B-тест. Никаких реальных переводов, seed phrases или регистрации. Попросить объяснить своими словами кто подписывает, кому уходят средства, где комиссия, что будет при отказе от подписи и распространяется ли схема на внешнюю игровую платформу.

**Пороги устанавливаются заранее как рабочие решения для маленького пилота, не отраслевые нормы:**

| Метрика | Числитель / знаменатель | Успех |
|---|---|---|
| Боль и подходящий канал | Люди с конкретным недавним затруднением сверки и контролируемым собственным каналом / 5 валидных участников | Не менее 3/5 |
| Понимание | Люди, верно объяснившие все пять вопросов без подсказки / 5 | Не менее 4/5 |
| Отсутствие опасной иллюзии | Люди, считающие devnet реальными деньгами или предполагающие доступ к чужим платформенным доходам / 5 | 0/5 |
| Следующее действие | Люди, согласившиеся на конкретную вторую сессию с обезличенной схемой своей команды / 5 | Не менее 2/5; простое «интересно» не засчитывается |

Успех требует **всех** порогов; он разрешает предложить узкий следующий эксперимент, не доказывает спрос или готовность к build. Если имеются пять валидных сессий и хотя бы один порог не выполнен — **measured miss**: остановить текущую формулировку, зафиксировать причину и одну возможную корректировку аудитории/обещания. Нельзя называть 2/5 вместо нужных 3/5 «почти успехом» или inconclusive. Недостаточно подходящих сессий, отсутствуют записи ответов или протокол испорчен подсказками — **inconclusive**; не записывать нули за ненаблюдавшиеся ответы. Повтор возможен только при новом evidence и доступном времени, в пределах исходной оценки + максимум двух исправлений.

Для истории ремонта аналогичный тест требует пары «мастерская + покупатель»: попросить отличить действующую, отозванную и подписанную неизвестным issuer запись; отсутствие такой пары означает пробел доступа. Для API сначала нужен один разработчик с обезличенными логами, показывающими реальное несоответствие платежа и запроса. Не переносить положительные ответы indie-команд на эти сегменты.

После будущего разрешения на реализацию отдельно измерить onboarding: из пяти подходящих начинающих тестировщиков число самостоятельно завершивших выбранное test-wallet действие за пять минут; целевой порог 4/5, ошибочных повторных оплат 0/5. Это будущий usability-тест, не выполненная проверка. Предварительно подготовленный кошелёк для трёхминутного демо не включать в метрику cold onboarding.

**Материальные уточнения для последующего выбора/планирования:**

1. **UX-1 — состояния и смена кошелька.** Разделить «Не подключён», «Подключаем», «Подключён: адрес». Если кошелёк заблокирован, дать действие «Откройте и разблокируйте кошелёк»; не притворяться, что блокировка определена, если провайдер не сообщает её. При смене адреса или сети после предварительного просмотра заново проверить полномочия и показать обновлённую сводку до подписи. В передаче записи ремонта нельзя предлагать подпись кошельком, который не является текущим держателем. Подключение само по себе не разрешает расход средств. На телефоне полный адрес доступен нажатием, а не только hover; кнопки копирования и Explorer различаются.
2. **UX-2 — чтение, пустота и устаревшее состояние.** Добавить «Платежей пока нет» с конкретным следующим действием и отдельно «Не удалось загрузить платежи». Для записи ремонта «не найдено» допустимо после успешного чтения нужной сети; ошибка RPC не означает подделку или отсутствие записи. Показать время последней успешной проверки статуса; устаревший результат не выдаётся за проверку отзыва сейчас. При возврате из кошелька или перезагрузке восстановить существующий заказ/signature. Общее правило навыка об optimistic UI не переносится на завершение оплаты/передачи: до подтверждения изменённое состояние помечается ожидаемым. Автоматический повтор чтения не означает новую подпись или повторную оплату.
3. **UX-3 — измеримость опасной иллюзии.** В первоначальном протоколе были пять вопросов о платеже, но метрика отдельно проверяет понимание devnet.
