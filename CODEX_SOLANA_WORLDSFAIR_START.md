# Codex + ProofPilot: от выбора идеи до Solana MVP

Подготовлено 07.10.2026. Язык работы — русский. Целевой первый конкурс — Crypto World's Fair, Solana Ecosystem Track + Superteam Kazakhstan Side Track.

## Как использовать

Скачай этот файл и положи в отдельную рабочую папку, которую откроешь в своём локальном Codex. Попроси выполнить **только промпт 1**. После выбора идеи отправь промпт 2; после одобрения архитектуры — промпт 3. Промпты 4 и 5 нужны для подготовки заявки и продолжения работы.

Начальная команда:

```text
Прочитай CODEX_SOLANA_WORLDSFAIR_START.md полностью. Выполни только промпт 1, соблюдая общие правила файла. Остальные промпты сейчас не запускай. Начни с проверки среды, ProofPilot и ближайших сроков регистрации.
```

Входить в аккаунты и подтверждать согласия придётся владельцу аккаунтов. Остальное Codex должен выполнять в пределах выданного задания без постоянных уточнений.

## Что удалось проверить

- ProofPilot — подходящий для задачи набор инструкций: поиск направлений, проверка спроса и конкурентов, планирование MVP, оценка готовности и подготовка заявки. Он помогает принимать обоснованные решения; качество спроса нельзя установить одним повторением AI-оценки.
- В проверенном README основной скилл устанавливается вместе с **36 вспомогательными**; отдельно доступны пять профилей стадий. Наличие скиллов не подтверждает работу MCP, аккаунтов или компиляторов.
- World's Fair — основной конкурс; Kazakhstan и KASE — дополнительные треки. Правила Colosseum ограничивают участника одной командой и одним проектом. Организатор Superteam KZ разрешает одному подходящему проекту участвовать в нескольких треках с отдельными заявками.
- На странице Kazakhstan Track указаны: регистрация до **8 октября**, Demo Day **10 октября**, глобальная подача **12 октября**. Время и часовой пояс местных мероприятий не указаны.
- Официальный глобальный дедлайн: **12.10.2026, 23:59 Pacific Time**, что соответствует **13.10.2026, 11:59 в Казахстане, UTC+5**. Это пересчёт времени, а не продление местного дедлайна. Планировать готовую заявку лучше на 11 октября.
- Kazakhstan Track требует доступный жюри GitHub, рабочее демо до **3 минут**, отдельный pitch до **2 минут**, заполненные профили и глобальную заявку. Слайды не заменяют показ продукта.
- Задача KASE, подтверждённая публикацией организатора: автоматизация корпоративных действий токенизированных облигаций — купоны, погашение и другие события. Полную страницу задания получить не удалось: API, sandbox и подробные критерии остаются непроверенными.
- У Superteam KZ также есть iDos Games Track, которого нет в исходном списке ссылок. Для него заявлены игровое демо, iDos Games AI и осмысленная интеграция Solana. Это возможное направление исследования, если выбранная идея действительно игровая.

Все сроки, правила и версии Codex должен перепроверить при запуске. Регистрация программы, запись на Demo Day и финальная подача — разные действия. Нельзя откладывать ближайшую регистрацию до завершения поиска идеи.

## Общие правила для всех промптов

1. Я начинающий разработчик: знаком с HTML, CSS и JavaScript; Solana пока не знаю. Работай в Codex, объясняй ключевые решения простым русским языком. Не переключай меня на другого AI-провайдера только потому, что такой скилл входит в пакет.
2. Для первого проекта основной фокус — глобальный World's Fair + Kazakhstan Track. Остальные направления сравнивай для совместимости; не создавай три конкурсные заявки с разными продуктами от одного участника.
3. Установку инструментов, создание отдельной папки и отдельного приватного GitHub-репозитория проекта разрешаю в рамках задания. Используй мой уже авторизованный GitHub. Не изменяй посторонние проекты, не удаляй мои скиллы и не меняй глобальные права Codex. Не публикуй приватный репозиторий и не отправляй финальную заявку без отдельной команды.
4. Для разработки разрешены localnet и devnet, установка необходимых локальных зависимостей и работа с отдельными тестовыми кошельками. Mainnet, реальные деньги и платные сервисы не входят в разрешение. Никогда не проси seed phrase, приватный ключ или токен в чате. Приложение подписывает пользовательские операции через кошелёк.
5. Используй субагентов, если они фактически доступны. Проверяй поддержку по текущей версии Codex и официальным документам; не выдумывай настройки. Если субагенты недоступны, честно обозначь последовательную работу по ролям. Одновременная смена роли в одном чате не считается независимым ревью.
6. У каждого агента должны быть задача, входные данные, ожидаемый результат и границы изменений. Не допускай параллельного редактирования одного файла или конфликтующих установок. Главный агент отвечает за интеграцию и итоговые решения.
7. Сохраняй исследование, решения и состояние работы в проекте. В новом чате сначала читай актуальные файлы. Каждый результат связывай с пунктом плана, а каждый технический вывод — с проверкой или источником.
8. Различай факт, предположение, гипотезу, вывод и неизвестное. Не придумывай пользователей, интервью, отзывы, статистику рынка, конкурентов, интеграции и результаты тестов. Отсутствие найденного конкурента не доказывает уникальность.
9. Не работай бесконечно. Соблюдай ограничения ProofPilot на исправления assessment: исходная версия и максимум две доработки. Новая оценка допустима при реально новых данных с объяснением причины, а не ради роста собственного балла. При повторяющейся ошибке меняй подход или фиксируй блокер.
10. Не задавай десятки вопросов. По умолчанию считай, что я один, бюджет внешних платных услуг — нулевой, время ограничено ближайшим Demo Day. Такие предположения не являются подтверждением конкурсной eligibility. Спрашивай только о материальных препятствиях, выборе идеи и согласовании плана.

```text
Если подключение пока невозможно, явно разрешаю ограниченное исследование по публичным источникам: отметь неполный setup и пробел Colosseum corpus. Не выдавай поиск в вебе за исследование его закрытого архива. Выполняй независимые задачи, пока ждёшь ручной вход.

Д. СУБАГЕНТЫ И ПРОВЕРКА ИДЕЙ
Поручи независимые задачи доступным агентам, максимум четыре одновременно:
1. Продукт/исследование — реальные проблемы, аудитория, конкуренты и путь к первым пользователям.
2. Solana/архитектура — необходимость блокчейна, минимальные primitives, внешние зависимости и выполнимость.
3. UX/демо — полный пользовательский сценарий, onboarding кошелька, понятность и эффектное рабочее демо.
4. Критик — причины отказаться, похожие проекты, слабые доказательства, правила конкурса и технические риски.

Для независимой проверки дай критику новый контекст с компактным evidence packet; не передавай желаемый ответ и не проси подтвердить мою любимую идею. Не называй его официальным жюри. Каждый вывод агента проверяй перед включением в итог.

Сделай один ограниченный цикл отбора: первоначальный assessment + максимум две доработки по evidence и замечаниям. На исследование отведи ориентировочно 60–90 минут агентной работы, затем выдай результат с пробелами. Не выдумывай точное прошедшее время, если не измерял его.

Первоначально сравни 5–7 существенно разных направлений. Отбрось идеи, где Solana декоративна, требуются недоступные партнёры/данные, слишком большой контракт или нет ясного пользователя. Для трёх финалистов ищи минимум три близких продукта/заменителя и похожие Colosseum-проекты при доступном архиве. Если поиск дал меньше, честно покажи покрытие.

Для каждого финалиста ответь:
— кто пользователь и в какой момент у него возникает проблема;
— как он решает её сейчас и что заставит его перейти;
— какие данные подтверждены, а что пока только гипотеза;
— точное отличие от найденных решений;
— зачем нужен Solana: что теряется при замене обычной базой и централизованной оплатой;
— один законченный MVP-сценарий и самое важное действие в реальной devnet-транзакции;
— один demo-момент, показывающий ценность, а не лишь 3D-обложку;
— как получить первые 5–10 потенциальных пользователей без вымышленных партнёрств;
— опаснейшее предположение, дешёвый проверочный эксперимент и измеримый порог успеха/отказа;
— работа до Demo Day, цена зависимостей и запасной вариант при сбое.

Можно сравнить, но не считать заранее выбранными:
• выплаты долей маленькой команде разработчиков игры через собственный канал платежей;
• переносимые записи ремонта/гарантии с проверяемым issuer и отзывом;
• узкий escrow одного этапа работы с прозрачными условиями и подтверждениями;
• квитанции и аудит платных API-покупок AI-агента.
Это гипотезы, не доказанно уникальные идеи. Не копируй готовый проект из Superteam Build. Для KASE сначала проверь полное задание, затем решай, есть ли разумное пересечение.

В доработках сначала проверь, что опровергает лидеров. Сужай аудиторию и MVP; не добавляй функции только ради необычности. Отдельно проверь UX и выполнимость к дедлайну. Сохрани исходные выводы и объясни, какие новые сведения изменили выбор. Не обещай идеальную идею, отсутствие конкурентов или победу.
```

## Промпт 3 — поэтапная реализация и проверка рабочего продукта

```text
Одобряю план docs/12-PLAN.md и выбранную архитектуру. Реализуй проект полностью по этому плану, соблюдая общие правила CODEX_SOLANA_WORLDSFAIR_START.md и AGENTS.md. Не запрашивай подтверждение каждого обычного этапа.

Прочитай актуальные state, spec, architecture, UX, security и plan. Отмечай для каждого Pxx статус, результат и проверку. При обнаружении существенной проблемы сначала предложи минимальное исправление внутри согласованного scope; изменение самой идеи или mainnet/платные действия требуют отдельного решения.

Используй solana-dev и другие реально установленные скиллы по задаче. Не загружай весь bundle в каждый контекст. Главный агент интегрирует; отдельные агенты могут заниматься Solana program, frontend/UX и review. Раздели файлы/ветки/worktrees по доступным возможностям. Согласуй API, IDL и типы перед параллельными изменениями. Не допускай конфликтующих коммитов и обновления lockfile несколькими агентами одновременно.

Сначала докажи вертикальный срез настоящей транзакцией. Не заменяй его toast-уведомлением, выдуманным hash или mock success. Следуй архитектуре хранения и подписания; backend не должен тайно управлять пользовательскими средствами.

После основных функций доведи UX: ясная иерархия, единые компоненты/иконки, мобильная версия, понятные суммы и сеть, пустые состояния, загрузки, отменённая подпись и восстановление после ошибки. Покажи ценность продукта сразу. Проверяй интерфейс в браузере и по скриншотам, а не только чтением CSS.

Проверки должны соответствовать рискам: права подписантов, допустимые состояния, повторная выплата/операция, недопустимые суммы, account substitution, refund/timeout если они входят в продукт, расчёты без ошибок floating point. Для UI проверь основной flow и реальные failure states. Не создавай бессмысленные тесты только ради количества.

Выполни подходящие build/typecheck/lint/tests и полный локальный/devnet smoke. Сохрани проверенный transaction signature/Explorer URL, program ID и network там, где применимо. Если часть не запущена, явно пометь её not verified. Потраченные усилия и написанные файлы не равны passed.

Поддерживай README с воспроизводимыми командами, .env.example без секретов, migration/seed при необходимости, dependency lockfile, безопасный .gitignore, docs и demo data. Проверь Git staging на credentials и тестовые wallet keypair files перед каждым push.

Не повторяй один и тот же неуспешный вызов бесконечно. После двух однотипных неудач изучи причину, попробуй иной подход или сохрани конкретный блокер. Не сообщай «всё готово», если ключевой flow не работает.
```
